# Boltrunner: профиль игрока

Модуль реализует регистрацию, вход с JWT и CRUD собственного профиля игрока на Rust. В браузере доступны три экрана: вход, настройки профиля и результат сохранения. Выбор персонажа сохраняется в профиле. Игровые модели и синхронизация выбора в матче находятся в [PR с персонажами](https://github.com/boltrun/boltrunner/pull/2); подключение API профиля к игровому клиенту выполняется отдельно.

## Запуск

Проверено на Rust 1.93.1. Выполнить из этой папки:

```sh
export BOLTRUNNER_JWT_SECRET="$(openssl rand -hex 32)"
RUST_LOG=boltrunner_profile_api=trace cargo run --locked
```

Открыть `http://127.0.0.1:8768/`. Создать аккаунт с ником до 20 символов и паролем длиной 8–128 байт. После входа выбрать цвет и персонажа, сохранить профиль.

Настройки через переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BOLTRUNNER_JWT_SECRET` | обязательна | Случайный секрет HS256, минимум 32 байта |
| `BOLTRUNNER_PROFILE_BIND` | `127.0.0.1:8768` | Адрес HTTP сервера |
| `BOLTRUNNER_PROFILE_DATA` | `data/users.json` | JSON-хранилище профилей и хешей |
| `BOLTRUNNER_LOG_FILE` | `log/log.txt` | Активный журнал |
| `BOLTRUNNER_LOG_MAX_BYTES` | `65536` | Максимальный размер журнала до ротации |
| `RUST_LOG` | `info` | Фильтр уровней журналирования |

Хранилище рассчитано на один серверный процесс. Изменения выполняются под mutex, записываются во временный файл и заменяют основной файл через rename. При ошибке записи состояние в памяти сохраняется.

## JWT

`POST /api/register` создаёт профиль и сохраняет пароль как Argon2id-хеш с случайной солью. `POST /api/login` проверяет пароль и выдаёт токен HS256 на 15 минут. Клиент передаёт его в заголовке `Authorization: Bearer <token>`. Сервер проверяет подпись, алгоритм, срок `exp`, издателя `iss`, аудиторию `aud` и идентификатор `sub`. Маршруты `/api/users/me` определяют пользователя из проверенного токена. Чужой идентификатор в запросе не принимается.

В интерфейсе токен хранится в памяти страницы; выход и перезагрузка удаляют его на клиенте. Смена серверного секрета делает выданные токены недействительными. Удалённый профиль не доступен с ранее выданным JWT. Refresh-токены и серверный список отозванных токенов в этом модуле не реализованы.

## OpenAPI и Swagger

Схема создаётся `utoipa` из типов и маршрутов в `src/http.rs`:

- `/openapi.json` — спецификация OpenAPI 3.1;
- `/docs` — Swagger UI;
- `Authentication` — регистрация и вход;
- `Profile` — чтение, изменение и удаление профиля;
- `Catalog` — доступные персонажи.

Для проверки защищённого маршрута получить токен через `/api/login`, нажать `Authorize` и вставить токен. Без него `/api/users/me` возвращает `401`. Swagger UI использует закреплённую версию ресурсов `swagger-ui-dist` 5.30.2 с CDN; для её загрузки нужен интернет.

## Тесты и качество

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Пакет `tests/service.rs` содержит 11 тестов, включая параметризованные наборы категорий входных данных. Проверяются ник, цвет и персонаж, границы пароля, конфликты, сохранение CRUD после перезапуска, хеширование, отказ хранилища, JWT и HTTP-маршруты. Отдельные тесты проверяют OpenAPI и ротацию без разрыва JSON-событий.

## Журналирование

`src/logging.rs` настраивает запись JSON-событий и ротацию по размеру. После превышения лимита активный `log.txt` становится `log.1.txt`, предыдущий — `log.2.txt`. Сохраняются два архива. Полное событие буферизуется до записи, чтобы JSON не разделялся между файлами.

- `trace`: чтение профиля;
- `debug`: сохранение хранилища;
- `info`: создание, обновление, удаление, успешный вход и обработка HTTP;
- `warn`: отклонённый вход и JWT;
- `error`: ошибка записи хранилища.

Пароли, их хеши и значения JWT не выводятся в журнал. `/log/`, `/data/`, `.env`, `/local/` и `/target/` включены в `.gitignore`. Активный `log/log.txt` не размещается в репозитории или на портале; для демонстрации ротации используются архивные журналы тестового запуска.

## Работа на разных машинах

На серверной машине запустить API с постоянным секретом, хранящимся в окружении процесса. Для доступа через командный reverse proxy оставить API на loopback и направить HTTPS-трафик на `127.0.0.1:8768`. Клиент на другой машине открывает HTTPS-адрес приложения. Интерфейс обращается к относительным `/api/...`, поэтому браузер и API используют один origin, без CORS-настройки.

Проверка: открыть страницу на клиентской машине, зарегистрироваться, войти, изменить цвет и персонажа, сохранить профиль; в Swagger проверить `401` без токена и `200` с JWT. Для отчёта сохранить снимки страницы и адреса сервера. Локальный запуск подтверждает HTTP-взаимодействие; проверка на двух машинах проводится после развёртывания на командном сервере.

Игровой клиент использует отдельный WebSocket-протокол Lightyear: `crates/client` отправляет ввод, а `crates/server` рассчитывает авторитетное состояние матча и возвращает изменения клиентам. При HTTPS игровой страницы соединение с игровым сервером должно использовать WSS.
